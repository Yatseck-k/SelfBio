# Whodoku: чек-лист проверки уровней

Прогонять регулярно (минимум раз в неделю и после каждой правки генератора, `config/story.php`, текстов дел). Раздел A выполняет бот сам, разделы B и C — вручную по командам.

Команды ниже запускаются внутри контейнера `php` (локально `docker compose exec php php artisan …`, на проде в `/opt/selfbio`). Про прод: сначала прочитать `selfbio-production-server`, перед правками данных сделать дамп базы.

## A. Автоматически (бот, `puzzles:review --all`)

Бот гоняется ночью на проде (cron 03:30 UTC, лог `/var/log/whodoku-review.log`). Ожидание: «не прошли: 0».

Блокирующие проверки (дело не публикуется):

| Код | Что проверяет |
|---|---|
| `structure` | карта и показания целы: комнаты, стены, предметы, гости |
| `author_solution` | авторская расстановка удовлетворяет всем показаниям и условиям |
| `unique_solution` | решение единственное (solver) |
| `logic_solvable` | дело решается логикой без перебора |
| `one_statement_each` | у каждого гостя ровно одно показание |
| `named_things` | названные предметы и комнаты есть на карте и различимы |
| `window_clear` | показание про окно указывает ровно на одно окно |
| `no_duplicate_statements` | показания не повторяются |
| `scene`, `scene_unique` | после расстановки ровно одна пустая клетка (место преступления) |
| `culprit_rule` | виновный однозначно следует из правила дела |

Проверки сюжетных глав (только для дел с `story_chapter`, блокирующие):

| Код | Что проверяет |
|---|---|
| `story_conditions` | дело содержит все условия главы из `config/story.php` |
| `story_size` | размер карты совпадает с главой |
| `story_texts` | в заголовке, уроке, брифинге и финале нет «ровно двое/трое» и неверного числа гостей |

Для всех дел: `victim_no_counts` — реплика жертвы не называет число людей.

Предупреждения: `gender_agreement`, `guests_distinct`, `rooms_connected`, `victim_card`, `hints`.

Дополнительно: `puzzles:review --all --unpublish` снимает с публикации несюжетные дела, не прошедшие бота; сюжетные только перечисляет.

## B. Согласованность текстов с картой

Пункты 1–5 теперь проверяет бот (`story_*`, `victim_no_counts`), вручную нужен только пункт 6. Раздел оставлен как описание того, зачем эти проверки.

1. **Брифинги и уроки глав** (`config/story.php`) не называют конкретных чисел условий («ровно двое», «ровно трое»).
   Автоматически: `php artisan test --filter=StoryTexts`.
2. **Число гостей.** На карте N×N гостей N−1. В брифингах не должно быть «девять гостей» для 9×9 и т. п. (тест `StoryTexts`).
3. **Реплики жертв** (`VictimFactory`) не утверждают того, чего правило не гарантирует. Инвариант генератора: в комнате места преступления стоит ровно один гость (виновный). Реплика не должна называть число людей.
4. **Условия главы.** Каждая сюжетная глава содержит все условия из `config/story.php` (`every_room`, `room_exact_count`, `room_limit`). Проверка: для каждой главы сравнить `conditions` с типами показаний дела (`EVERY_ROOM_HAS_TOKEN`, `ROOM_TOKEN_COUNT`, `ROOM_TOKEN_LIMIT`). Недостающие заменяет `puzzles:regenerate --apply`.
5. **Размер карты** сюжетной главы совпадает с `size` из конфига.
6. **Названия комнат и предметов** в брифингах, итоговом тексте дела и показаниях совпадают с картой (глазами пройти 3–4 случайных дела).

## C. Прохождение глазами игрока (вручную, 10 минут)

Выбрать 3–5 дел: одно с условиями «в каждой комнате…», одно с окном, одно на 8×8 или 9×9, одно из последних сгенерированных. Для каждого:

1. Прочитать все показания по очереди: каждое понятно без догадок? Где окно, угол, «выше/ниже/правее/рядом» — однозначно?
2. Условия дела («в каждой комнате кто-то был», «ровно столько-то», «не больше стольких») читаются и совпадают с брифингом.
3. Расставить гостей по решению: игра принимает расстановку, показывает «дело раскрыто» и итоговый текст.
4. Нарочно поставить гостя неверно: игра не засчитывает и не противоречит сама себе.
5. На телефоне: карта и показания читаются, подписи не перекрывают гостей и мебель, тёмная тема не ломает цвета.
6. Подсказки (3 шт.) не подсказывают ложного и не выдают решения целиком.

## D. Состояние и данные

- Сюжет: 50 глав, у каждой есть опубликованное дело (`story_chapter` уникален); глава N открывается после решения N−1.
- В очереди нет дел в статусе `draft`/`failed` без причины; у релизов (`ReleaseService`) на ближайшие дни есть дело.
- Результаты игроков (`PlayerCaseResult`) привязаны к существующим делам (после `puzzles:regenerate` slug и место дела сохраняются).
- Нет ошибок 5xx в логе nginx и в `storage/logs` по маршрутам `/api/puzzles*`.

## E. Обращения игроков

Админка → Whodoku → «Обращения игроков»: разобрать новые обращения. Для каждого: «Проверить дело ботом», затем «Решено» или «Отклонить» с заметкой. Если жалоба подтвердилась, найти причину и добавить проверку в раздел A или B, чтобы класс ошибки не повторялся.
